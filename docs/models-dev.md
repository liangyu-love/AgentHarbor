# models.dev model metadata

AgentHarbor resolves model capabilities and prices through one resolver fed by
the [models.dev](https://github.com/anomalyco/models.dev) catalog. This document
describes where the data comes from, how a value is chosen, and what is never
derived from a model's name.

## Data sources

| Source | Where it lives | Notes |
| --- | --- | --- |
| Bundled snapshot | `src-tauri/assets/models-dev.snapshot.json` | Committed, generated by `node scripts/build-models-dev-snapshot.mjs`; used offline and as the last resort. |
| Runtime cache | `<app data>/models-dev.json` | Written atomically after a successful download; always wins over the bundled snapshot when it is whole and valid. Never merged with it. |
| Refresh | `load_models_dev_status` / `refresh_models_dev_catalog` commands and an hourly background check | 24-hour validity, conditional `If-None-Match` requests, failures keep the last valid catalog and report `lastRefreshError`. |

Update the bundled snapshot explicitly for a release. Normal builds only read
the committed file and never require network access.

## Matching

`model_metadata::candidates` turns a configured model ID into an ordered list of
candidate identities, recording every step (`pathPrefix`, `channelMarker`,
`knownChannelSuffix`, `effortSuffix`, `tagSuffix`, Bedrock `regionPrefix`, …).
Versions, dates and `-preview` suffixes are never removed. Matching kinds:

- `explicit` – a user-bound `{providerId, modelId}`; a stale binding fails closed.
- `exact` / `normalized` – a scoped match inside the provider's configured
  capability catalogs (`catalogProviders`).
- `consensus` – an automatic generic reference limited to supported publisher
  catalogs; only agreeing fields are filled in, listed as `catalogGeneric`.
- `ambiguous` – same-priority candidates disagree; agreeing fields are kept and
  the rest are reported as conflicts instead of guessed.
- `unmatched` – nothing matched; clients see the shared fallback, marked as such.

Automatic scopes prefer the recognized model publisher. Aggregator catalogs
require a saved user binding. Scoped canonical identities declared by the
catalog are considered after direct IDs, with active entries preferred over
deprecated aliases. Known thinking/effort suffixes can be normalized for
capabilities while keeping the original request ID and version intact.

When every normal candidate misses inside Google's catalog, a Gemini ID that
omits `preview` may reference the active, same-version `<candidate>-preview`
entry. The trace marks this as `previewReference`, not a publisher-declared
alias. No version, dated preview or custom-tools variant is guessed; deprecated
entries are excluded and case conflicts remain visible. This capability-only
reference never changes the actual request ID or establishes preview pricing.

Fast variants follow the same separation between request identity and metadata.
An exact full Fast record or an explicit `catalogRef` takes precedence. If the
full variant has no capability match, a terminal `-fast`, `_fast`, `@fast` or
`:fast` marker (case-insensitive) may reference the same-version base model's
context window. This is a `speedVariantReference` step with the field source
`catalogSpeedReference`. The resolver keeps the configured request ID and its
display name. It does not borrow the base model's input limit, output limit,
reasoning support, reasoning levels or price. Versions, dates, `preview` and
other product qualifiers remain part of the identity; an unavailable or
conflicting base context stays unknown rather than selecting another version.

Prices require an independent billing binding (`priceCatalogProvider` or a model
`priceRef`) or an explicit user price. Capability mappings and capability
references never establish billing prices. Without a billing binding, price
remains unknown. A `priceRef` overrides the provider's billing scope; otherwise
the full upstream model ID is tried first, followed by price-safe candidates in
their original order, independently of the capability match. Prices are never averaged or
borrowed across providers, and `:free`/`@fast`-style tags never borrow the base
model's price.
The safety check covers the entire candidate reduction path, including combined
prefixes and tags. Catalog agreement compares every stored price field and tier;
a conflict stays unknown with an explanation.

Claude Desktop routing uses the effective context from this shared resolver to
offer the extra 1M menu option. A context of at least 1,000,000 tokens must come
from an evidenced source, such as a user override, provider setting, upstream
declaration, applicable official snapshot or catalog reference. The shared
fallback is insufficient. Messages, Chat Completions and Responses targets use
the same capability check; the checkbox remains off by default. This Desktop
rule does not widen the ordinary router's existing Claude 1M protocol boundary.
Chat/Responses conversions do not invent a 1M request parameter or forward
Claude beta headers. Client rendering and actual upstream context acceptance
still require live verification.

## Field precedence

For every field the resolver reads, in order:

1. Explicit user overrides (`overrides.*`).
2. Provider-level settings (`contextWindow`).
3. Real upstream declarations collected from the provider's model list.
4. The signed-in Codex account snapshot, and only when the provider targets the
   official endpoint.
5. models.dev exact/normalized match.
6. Unambiguous generic reference.
7. The shared fallback (`128 000` / `8 192`), clearly labelled `fallback`.

Newly fetched output-only declarations remain upstream data even without a
context declaration. Each resolved catalog field carries the reference and date
of a record that actually declares that field, rather than another matched record.

Compression thresholds follow `model → provider → global` inheritance with a
default of 90% of the effective prompt budget (`limit.input` when the catalog
provides it, otherwise `limit.context`). Fixed token thresholds never move on a
catalog refresh; percentages are recomputed.
The effective budget never exceeds the final context override; raw input/context
values remain visible separately. Router failover reads the proxy's existing
same-model candidate predicate and limits only that relay entry's budget.
Unknown candidate budgets are called out without disabling the candidate.

The provider editor resolves selected models from its unsaved draft through
`preview_newapi_model_resolutions`. Context/input/output placeholders and the
catalog reference show the shared resolver's values; compression shows the
effective source and threshold. The preview reads local snapshots and stored
policy without writing or fetching, and never sends credentials. Automatic
values remain display-only: saving leaves manual overrides and explicit catalog
references empty until the user edits them. Pending models are resolved when
added, independently of the size of the fetched list.

Native Codex applies a shared minimum threshold across the active provider's
selected Responses models. The preview shows each model's suggestion, the
planned shared threshold, the value read from config, the limiting models and
sync state. Models outside that configuration are marked inactive.
Catalog generation, shared planning and configuration matching reuse one native
configuration plan captured from the same models.dev and applicable official
snapshots. OpenCode receives that same applicable official source when configured
by the application. An invalid policy, unknown budget or `clientDefault` model
prevents injecting a global shared threshold; the model stays selectable and the
user's values stay stored. `compressionSharedPlan` names the state and blocking
models. A written router catalog is reported separately from an active config:
only an enabled router whose config references that catalog can be applied.

`budget_tokens.min` uses `-1` upstream for "unset"; the snapshot drops it and
the deserializer treats non-positive values as missing.

The snapshot keeps limits, reasoning options, the full cost structure
(including tiers and `context_over_200k`), modalities, status, dates and
`canonical_model_id`. Descriptions, logos and benchmarks are dropped.
Runtime refresh converts the public provider-keyed response into the same typed
snapshot before validation and atomic publication. Both refresh paths use the
SHA-256 of the source bytes as the content revision; internal snapshots continue
to be the only accepted cache format.

## Usage ledger

New records use `schemaVersion: 1`, correlate `requestId` with route diagnostics,
and give every upstream attempt its own `attemptId`. They persist the request's
pricing snapshot (including its reference and revision) and selected conditional
rates. Missing usage has an unknown cost; explicit zero usage and zero rates
remain zero. Missing priced categories and incomplete usage produce a partial
amount when a useful subtotal exists. Reliable usage on failed responses is
still charged. Existing records retain their amounts and remain readable; catalog
and manual price changes never reprice the ledger. Archive regression checks
preserve micro-USD amounts and priced/unpriced counts through repeated compaction.
Streaming counters are merged before their final normalization, so cache details
reported later reduce uncached input without double billing. `pricedCount` stays
the count of recorded subtotals for compatibility; `fullyPricedCount`,
`partialCount` and `coverageUnknownCount` describe their coverage. Older archives
retain their exact amounts and mark the coverage of priced requests unknown.
Summaries, trends and model/provider views show partial and unknown coverage.

`week` retains Monday-based semantics. `lastSevenDays` covers today and the six
preceding local calendar days; its start/end dates and the local timezone offset
are returned in the payload. The seven-day cost card consumes this separate total.

Resolved prices, pricing snapshots and applied rates retain `inputAudio`,
`outputAudio`, `tiers` and `contextOver200k`, with matching TypeScript contracts.
Audio usage is not currently observed, so an audio price makes settlement
incomplete rather than silently claiming full pricing. The original rates remain
available to consumers; historical amounts are never recomputed.

## Migration

Store schema v8 introduces `overrides`, `catalogRef`, `priceRef` and
`compression`. The one-time migration:

- moves `metadata_source = "manual"` values into `overrides`,
- demotes historical `upstream` values to `legacy` (they may have been
  overwritten by the removed local defaults),
- clears auto-filled `local`/`catalog` limits so the resolver re-derives them,
- converts a non-empty `autoCompactLimit` into a provider `tokens` policy.

Before replacing a pre-v8 store, the migration saves the original bytes in
`<app data>/newapi-providers.pre-v8.dat` using the same encrypted storage policy.
Backup failure aborts the migration, and later reads preserve the first backup.
Legacy manual values are promoted only during that versioned migration. Clearing
`overrides.*` afterward never resurrects top-level values. The model editor can
independently edit or clear context, input, output, reasoning and default effort.

Back up `<app data>/newapi-providers.dat` before a downgrade; user IDs,
protocols, aliases and overrides are never cleared by the migration.

## 2026-10-03 自动匹配边界补充

- `nova-*` 属于原厂 `nova` 目录；`amazon.nova-*`、已识别区域前缀的 Amazon Nova ID 和 `amazon/nova-*` 可使用 Bedrock 的 Amazon 自有模型记录。该规则不把 Bedrock 托管的 Claude 等其他品牌加入自动匹配来源。
- 聚合服务商的 `canonicalModelId` 不参与自动判断原厂身份；用户显式绑定目录仍按用户选择解析。
- 原厂白名单中的部分供应商 ID 是预留项：嵌入快照缺失时保持严格未匹配，后续目录更新可直接使用。当前缺失的 ID 为 `microsoft`、`baidu`、`01-ai`、`internlm`、`baichuan`、`bytedance`。
- `MatchKind::Invalid` 表示显式引用无效，不回退到其他目录冒充匹配。
- `-max`、`-ultra`（含下划线变体）保留为产品型号；`(max)`、`:max`、`@ultra` 等明确标记仍可作为思考档位归约。候选最多 16 个，深层装饰可能保持未匹配，不放宽到其他品牌或第三方。
- API 主机索引随 Catalog 构建，按主机精确查询，不在每次请求中重新解析所有供应商 URL。
